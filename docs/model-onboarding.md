# Onboarding a model onto storytree

How to bring a new model — and, if it needs one, a new harness — onto this system.

Read this when someone says *"can we use &lt;model&gt; here?"*. It answers where the model plugs in,
what it has to be able to do, what you have to build, and what you get for free.

> **Worked example.** Every step below has a live instance: **Kimi K3 via Fireworks AI, driven by
> OpenCode**, onboarded 2026-08-07. Its exact commands are in
> [§5](#5-worked-example--kimi-k3-via-fireworks-in-opencode).

---

## 1. First decide WHICH seam — this is the whole fork

Storytree has two, and they are not interchangeable. Onboarding cost differs by an order of
magnitude, so get this right before you touch anything.

| | **Outer loop** (interactive) | **Inner loop** (`PhaseAuthor` leaf) |
|---|---|---|
| What it is | A model driving a *session* — orienting, deciding, landing work | A model authoring *inside one phase* of the prove-it-gate |
| Who owns the loop | The human (ADR-0030) | The deterministic spine (`packages/orchestrator`) |
| Examples today | Claude Code, Codex CLI, **OpenCode** | `ClaudeAgentAuthor`, `CodexPhaseAuthor`, the owned loop |
| Signs verdicts? | No — it *runs* the gate | No — the **spine** observes red/green (ADR-0020) |
| Code change needed | **None.** Config only | Yes — a new `PhaseAuthor` impl + the `LiveRuntime` union |
| Needs an ADR? | No | **Yes** — it admits a new funded runtime |
| Effort | ~an hour | A build, with an ADR and a live smoke |

**Most requests are the outer loop.** "I want to use model X to work on storytree" almost always
means *"give X a terminal and let it drive"* — which is configuration, not a build. Do not reach for
the leaf seam unless the ask is specifically *"prove units with X behind the gate"*.

### The outer loop is nearly free, and here is why

A new interactive harness inherits storytree's whole orientation surface without you writing a word
of it:

- **`AGENTS.md`** at the repo root is the canonical `session-orchestrator` agent rendered for
  non-Claude harnesses (ADR-0291), generated by `pnpm build:guidance`. OpenCode, Codex and most
  other agentic CLIs read `AGENTS.md` by convention — so a new harness gets the *same* operating
  discipline Claude Code gets from `CLAUDE.md`, from the same single Library source.
- **The CLI** (`pnpm storytree …`) is harness-agnostic. Any model with shell access can explore the
  Library, read arcs, declare on the notice board and run the gate.

So the outer-loop job reduces to: *make the harness talk to the model, and point it at the repo.*

### The inner loop is a build (do not do it by accident)

The leaf seam is `packages/agent/src/phase-author.ts`. Admitted live runtimes are a typed union:

```ts
export type LiveRuntime = "claude" | "codex";
```

Adding a third means a new `PhaseAuthor` implementation, widening that union, `--runtime` plumbing
in `packages/drive`, and an ADR that says why the runtime is admitted and how it is funded.
Precedent, in order: **ADR-0177** opened the seam to Cursor, **ADR-0198** retired that leaf
(both now `superseded`), **ADR-0232** added the Codex leaf and is the live template to copy.

## 2. The capability bar

Before configuring anything, check the model can actually do the job. Ask the provider's API, don't
trust a marketing page:

```bash
curl -s https://<provider>/v1/models -H "Authorization: Bearer $KEY"
```

Cross-check against the **[models.dev](https://models.dev/api.json) registry**, which most agentic
harnesses (OpenCode included) use as their model catalogue — it carries context/output limits,
pricing, reasoning options and capability flags that the provider's own `/models` endpoint omits.

| Requirement | Why | Kimi K3 |
|---|---|---|
| **Tool / function calling** | Non-negotiable. An agent with no tools is a chatbot | ✅ `supports_tools: true` |
| **Large context** | `AGENTS.md` alone is ~21 KB before any repo file | ✅ 1,048,576 in / 131,072 out |
| **OpenAI-compatible `/v1/chat/completions`** | What every harness's generic adapter speaks | ✅ |
| **Streaming** | TUIs need it to feel alive | ✅ |
| Vision | Only if you want it reading screenshots/UAT evidence | ✅ `supports_image_input` |

Then **prove tool-calling end to end** before wiring a harness — one `curl` with a `tools` array,
and confirm the reply carries `finish_reason: "tool_calls"`. A model that answers prose instead of
calling the tool will fail silently and confusingly inside a harness.

## 3. Credentials

**The API key never enters the repo.** Two places are correct, and which one depends on who reads
it:

1. **The harness's own credential store** — preferred when the harness has one. OpenCode uses
   `~/.local/share/opencode/auth.json`; it is outside the repo and outside any worktree.
2. **`~/.storytree/secrets.json`** — the house rotation point (`packages/drive/src/secrets.ts`),
   read by the *storytree CLI*. Hydration is gated by an explicit `SECRET_KEYS` allowlist, so a key
   only lands in `process.env` if it is on that list. Add a key here **only when storytree's own
   code needs it** — i.e. when you build an inner-loop leaf. An interactive harness reads its own
   store, not this file, so adding an unused key here is speculative wiring.

Source of truth for this project's keys is GCP Secret Manager:

```bash
gcloud secrets versions access latest --secret=<name> --project=635716509357
```

Committed config references a secret, never contains one — `{env:VAR}` or the harness's store.

## 4. The onboarding checklist

1. **Pick the seam** (§1). Outer loop → continue. Inner loop → write the ADR first.
2. **Verify the capability bar** (§2), against the provider's API.
3. **Install the harness.**
4. **Store the credential** (§3) — never in the repo.
5. **Check the harness's model registry** (`https://models.dev/api.json`) before writing any provider
   block — most providers are already there with correct limits and cost. Pin the model in the
   project config, committed and secret-free. Hand-roll a provider only if it is genuinely absent.
6. **Prove it end to end**: a real run that makes the model *use a tool* against this repo.
7. **Confirm orientation**: the harness reads `AGENTS.md` (or add a pointer if it uses another
   filename).
8. **Record it**: append the increment to the owning arc, and document any deviation here.

## 5. Worked example — Kimi K3 via Fireworks in OpenCode

Landed 2026-08-07. Seam: **outer loop**. Code changes: none.

### Install

```bash
npm install -g opencode-ai
```

### Credential

The Fireworks key lives at `projects/635716509357/secrets/fireworks-ai-storytree`. It goes into
OpenCode's own store — not the repo, and not `~/.storytree/secrets.json`, because nothing in
storytree's own code calls Fireworks (§3):

```bash
opencode providers login --provider fireworks-ai
```

That prompts for the key. Paste the value of:

```bash
gcloud secrets versions access latest --secret=fireworks-ai-storytree --project=635716509357
```

Verify with `opencode providers list` — it should report `fireworks-ai  api`. The provider id is
`fireworks-ai`, **not** `fireworks`; it must match the registry id exactly or the credential binds
to nothing.

### Provider config — there isn't one

`fireworks-ai` is already a first-class provider in the models.dev registry, and the registry
already carries both Kimi K3 entries. **No provider block is needed.** The committed
[`opencode.json`](../opencode.json) at the repo root only pins which model storytree work runs on:

```json
{
  "model": "fireworks-ai/accounts/fireworks/models/kimi-k3",
  "small_model": "fireworks-ai/accounts/fireworks/routers/kimi-k3-fast",
  "instructions": ["AGENTS.md"]
}
```

- `model` — the main agent. `small_model` is the cheaper router used for titles and summaries.
- Fireworks model ids are themselves paths, so the fully-qualified reference reads
  `fireworks-ai/accounts/fireworks/models/kimi-k3`. That is correct: the harness splits provider
  from model on the *first* `/`.
- `instructions` names `AGENTS.md` explicitly. OpenCode picks it up by convention anyway; stating it
  makes the dependency visible rather than magic.

The file is secret-free, so it reproduces on any machine that has the credential.

### Prove it

```bash
opencode models | grep kimi
```

```bash
opencode run "Read package.json and tell me the pinned pnpm version. Do not modify any files."
```

A pass looks like a `Read` tool call followed by the correct answer — tool use, not a guess.

### Windows ARM64: the TUI needs the x64 binary

On an ARM64 Windows box the npm install resolves to `opencode-windows-arm64`, whose bundled runtime
has **no FFI** — so the terminal UI dies at startup:

```
Failed to initialize OpenTUI render library: bun:ffi dlopen() is not available in this build (TinyCC is disabled)
```

Only the TUI is affected. `opencode run`, `opencode serve` and the model itself are fine, which is
why this is easy to misdiagnose as a bad credential or a bad model id.

The `opencode-windows-x64` build *does* have FFI and runs correctly under Windows' x64 emulation.
`npm install -g opencode-ai --cpu=x64` does **not** work — a postinstall arch check refuses it — so
swap the binary the launcher shim calls:

```bash
G="$(npm root -g)/opencode-ai/bin"
cd "$(mktemp -d)" && npm pack opencode-windows-x64 && tar -xzf opencode-windows-x64-*.tgz
cp "$G/opencode.exe" "$G/opencode-arm64.exe.bak"   # reversible
cp package/bin/opencode.exe "$G/opencode.exe"
```

Stop any running `opencode` process first or the copy fails with *device or resource busy*. Re-do
this after any `opencode upgrade` — an upgrade restores the arm64 binary and the TUI breaks again.

Two workarounds if you would rather not swap the binary:

```bash
opencode web     # full UI in the browser — same server, no TUI
opencode run "…" # one-shot headless
```

### Then just drive it

```bash
opencode
```

OpenCode reads `AGENTS.md` at the repo root, so Kimi K3 boots with the same
`session-orchestrator` discipline every other session runs.

### What this deliberately did NOT do

Kimi K3 is **not** a `PhaseAuthor` leaf. `--runtime kimi` does not exist, and
`storytree node build --live` cannot route to it. That is the inner-loop seam of §1 and needs its
own ADR. Kimi K3 drives the outer loop: it runs the gate, it does not sign verdicts.

## 6. Gotchas

- **Check the registry before hand-rolling a provider — and don't use `opencode models` to check.**
  This one cost real time during the Kimi K3 onboarding. `opencode models` lists only providers you
  already hold a *credential* for, so a provider absent from that output looks unsupported when it
  is merely unauthenticated. Fireworks was read as missing on exactly that evidence and defined by
  hand as a generic OpenAI-compatible provider. It worked — and was still wrong: the built-in entry
  carries the real output limit (131,072, where the hand-rolled guess said 65,536), the
  reasoning-effort options, `temperature: false`, `interleaved.reasoning_content` for rendering
  thinking, and per-token cost that makes `opencode stats` meaningful. A hand-rolled block silently
  loses all of it. **Query the registry directly** — `curl -s https://models.dev/api.json` — and only
  define a provider by hand when it genuinely isn't there.
- **Provider id must match the registry exactly.** `fireworks-ai`, not `fireworks`. A credential
  stored under the wrong id binds to nothing, and the failure looks like an auth error.
- **Model ids with slashes.** Fireworks ids are paths (`accounts/fireworks/models/kimi-k3`). Harnesses
  that join provider and model with `/` produce a double-barrelled reference. That is correct, not a
  typo.
- **Windows ARM64: the harness's TUI may be the only broken part.** On this dev machine `opencode`
  dies at startup with *"Failed to initialize OpenTUI render library: bun:ffi dlopen() is not
  available in this build (TinyCC is disabled)"*. The `opencode-windows-arm64` binary ships without
  FFI, so the terminal UI cannot load its native renderer — while the server, the model and the
  headless path all work fine. **Don't read a dead TUI as a dead install**; check `opencode run …`
  and `opencode serve` before concluding anything about the model or the credential. The fix and the
  two workarounds are in [§5](#windows-arm64-the-tui-needs-the-x64-binary).
- **A fresh worktree has no `node_modules`.** `pnpm install` in it before any `pnpm storytree …` or
  `pnpm db:*` command, or they fail with errors naming the wrong cause.
- **Context size is not context quality.** A 1M window does not make a model good at this repo. Judge
  a new model on a real unit driven to green, not on the spec sheet.
